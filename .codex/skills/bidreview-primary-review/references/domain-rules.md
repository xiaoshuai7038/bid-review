# Domain Rules

## Canonical Flow

当前首轮审查按下面的逻辑理解：

1. `requirements` 阶段：
   - 只读招标文件
   - 从关键章节提取硬性要求
   - requirement 去重后最多 40 条
2. requirement 补齐阶段：
   - 若招标条款未显式覆盖“主体一致性”，仍要补 1 条通用主体基线 / 全文一致性 requirement
   - 对第六章模板文书和表单，必须额外补足模板字段 requirements，不能只写一条笼统“响应格式”
3. findings 阶段：
   - `compliance`：常规逐条合规问题
   - `context`：主体基线、角色/位置错位、模板字段角色错误、跨全文冲突
   - `semantic`：字段标签和值类型不匹配
4. 合并阶段：
   - 只保留事实级去重后的 findings
   - 输出 `summary.review_scope`

## Requirement Extraction

优先覆盖招标文件中的：

- 第二章“投标人须知”
- 技术要求章节
- 第六章“投标文件格式”
- “评标办法前附表”或等价评分/资格审查章节

requirements 至少要覆盖：

- 资格资质
- 类似项目业绩
- 报价与税务
- 工期 / 交付
- 签字盖章
- 格式完整性
- 技术响应
- 服务承诺

对第六章模板文书和表单，必须单独覆盖以下 requirement 类型：

- 收件人 / 抬头字段
- 项目标识字段（项目名称、招标编号）
- 主体与签署字段（投标人、法定代表人、委托代理人）
- 投标保证金与基本账户字段
- 技术 / 商务偏离表字段

## Subject Baselines

先建立主体基线，再写 findings：

- 招标人 / 采购人：
  - 名称
  - 税号 / 统一社会信用代码
  - 银行账户信息（如有）
- 投标人：
  - 名称
  - 统一社会信用代码
  - 税号 / 纳税人识别号
  - 法定代表人
  - 授权代表 / 委托代理人
  - 开户银行
  - 账户名
  - 账号
- 联合体成员（如有）：
  - 成员名称
  - 身份和角色

优先用营业执照、封面、投标函、资格审查申请书、授权委托书、保证金或账户证明等权威位置建立基线。

## Findings Lane Boundaries

### Compliance

这一层重点检查：

- 资格、业绩、报价、工期、技术、服务、签章、格式等常规不符合项
- requirement 对应的明确缺项、漏项、偏离、冲突

这一层不要单独输出：

- 纯主体串用 / `致：` 抬头错对象
- 纯跨全文主体字段冲突
- 纯字段标签和值类型不匹配

### Context

这一层重点检查：

- 角色 / 位置错位
- `致：`、收件人、抬头、落款主体错误
- 招标人 / 投标人 / 招标代理机构名称串用
- 项目名称 / 招标编号引用其他项目
- 同一主体名称、法定代表人、账号、开户信息跨全文冲突

### Semantic

这一层只检查字段标签和值的语义类型是否匹配，例如：

- `开户银行` 填成公司名称或自然人姓名
- `账户名` 填成银行名或账号串
- `账号` 填成主体名称
- `法定代表人 / 授权代表` 填成单位名称
- `统一社会信用代码 / 税号` 填成普通文本

如果字段期待“公司名”，实际也确实填了“公司名”，只是公司填错了，这属于 `context`，不属于 `semantic`。

## Severity

- `non_compliant`
  - 明确不符合
  - 明显主体错位
  - 模板字段误填
  - 关键字段缺失
- `risk`
  - 有较强风险但证据还不完全闭合
- `needs_manual`
  - 证据不足、模糊或截图不可读

若已经有明确字段和值，不要继续用泛化 `needs_manual` 替代本应直接下结论的问题。
